## 1. Source Classification

Every parameter in this specification is tagged with one of:

| Tag | Meaning |
|---|---|
| `[EXTERNAL]` | External authoritative source (GTFS feed, Annual Report, news) |
| `[DERIVED]` | Computed from an external source |
| `[SYNTHETIC]` | Project assumption (no verified source) |
| `[MODEL LIMITATION]` | Deliberate simplification |

**Rule:** No parameter is claimed as `[DPR]` because the DPR document is not in the project. Values previously tagged `[DPR]` are now relabeled `[EXTERNAL]` (if verified) or `[SYNTHETIC]` (if assumed).

## 4. Data Quality Notes

### 4.1 GTFS Filtering

GTFS has **255 weekday trips total** in `trips.txt`.

Of those:

- **250 trips** depart between 06:00 and 23:00 (passenger service window) — **used in model**.
- **5 trips** depart outside 06:00–23:00 (early positioning runs: 05:00, 05:20, 05:45, 05:57; late finish-up: 23:22) — **excluded as non-passenger movements**.

### 4.2 UP/DOWN Direction

- `UP` = ALVA → TPHT (increasing station sequence).
- `DOWN` = TPHT → ALVA (decreasing station sequence).

Derived from `stop_id` of first/last stop in `stop_times.txt`, with fallback to `direction_id` from `trips.txt`.

## 5. Hard Constraints (R1–R12)

### R1 — Service Coverage `[EXTERNAL]`

For each hour `h` and direction `d`:

```python
count(trips[h][d]) >= required_departures[h][d]
```

Where `required_departures[h][d]` is from `data/hourly_service.csv`.

**Validator check:** Count departures per hour and direction; compare to hourly CSV.

### R2 — Headway `[SYNTHETIC]`

**R2a — Design headway (hard):**

```python
departure[i+1] - departure[i] >= 2 minutes
```

For consecutive trips in the same direction.

**R2b — Target headway (soft — objective O2):**

```python
minimize |actual_headway - target_headway[h]|
```

**Validator check:** No two departures in the same direction are closer than 2 minutes.

### R3 — Operating Window `[EXTERNAL]`

```python
06:00 <= departure <= 23:00
```

**Arrivals may extend past 23:00.** Only departure is constrained.

**Validator check:** All departure times within 06:00–23:00.

### R4 — Fleet Availability `[EXTERNAL]`

Only rakes with `status = "service"` can be assigned trips.

Rakes with `status = "maintenance"` are blocked.

**Validator check:** Peak-hour active rake count ≤ `SERVICE_RAKES` (= 18). Matches implementation in `solver/constraints.py add_r4_fleet_availability`, which blocks all rakes with `status != "service"`.

### R5 — Rake Non-Overlap `[EXTERNAL]`

For each rake, no two activities overlap:

```python
model.AddNoOverlap(rake_intervals[rake_id])
```

**Validator check:** No rake is assigned overlapping time intervals.

### R6 — Terminal Turnaround `[SYNTHETIC]`

```python
turnaround_time >= 5 minutes
```

Applied between every consecutive trip on the same rake.

**Validator check:** All turnaround gaps ≥ 5 minutes.

### R7 — Running Time `[DERIVED — GTFS]`

```python
one_way_running_time = 50.47 minutes
```

Median of 412 GTFS trips.

Rounded to 50 minutes in the integer-minute model.

**Validator check:** Each trip's duration = 50 minutes.

### R8 — Depot Capacity `[SYNTHETIC]`

**Info Park-2:**

```python
rakes_stabled <= 2
```

**Muttom:** `UNBOUNDED_FOR_V1`

**Validator check:** SKIPPED — no stabling assignment in V1.

### R9 — Maintenance Exclusivity `[SYNTHETIC]`

A rake in maintenance cannot be assigned passenger service.

**Validator check:** No rake with `status = "maintenance"` is assigned a trip.

### R10 — Maintenance Threshold `[SYNTHETIC]`

A rake with:

```python
cumulative_mileage >= 1_000_000
```

is due for maintenance.

**Validator check:** No rake over the threshold is assigned a trip.

### R11 — Deadhead `[SYNTHETIC — NOT CONFIGURED]`

Not modeled in V1.

### R12 — Non-Service Window `[EXTERNAL]`

```
00:00–06:00: no passenger service
```

**Validator check** : No trip departs before 06:00. Arrivals may extend past 06:00 (or past 23:00 for last trips — see R3).

## 9. Validation Layer

Independent of CP-SAT's own status. Every hard constraint is rechecked from the CSV.

**Current coverage (10 of 12):**

- R1, R2a, R3, R4, R5, R6, R7, R10, R12 — all PASS.
- R8 — SKIPPED (no stabling assignment in V1).

**Not independently validated (though implemented in solver):**

- R9 — Maintenance exclusivity: implemented as `status != "maintenance"` filter in R4, but not separately re-checked by validator. Baseline has no maintenance rakes with trips, so vacuous.
- R11 — Deadhead: not configured.

**Result:** 9 PASS + 1 SKIPPED, Overall PASS (250 trips).

## 10. Model Limitations (V1)

1. **Muttom depot capacity** — unbounded in V1.
2. **Deadhead** — not configured.
3. **Optimality gap** — reported (was approximately 93% at 300s timeout). Claims about "optimized" cite the actual gap.
4. **Crew scheduling** — deferred to Phase 3.
5. **ML/XGBoost** — deferred; no dependency.
6. **Passenger demand** — no demand model; O1 uses a headway-based proxy.
7. **UP/DOWN meaning** — derived from GTFS first/last stop.
8. **Maintenance threshold** — synthetic (1M km), no verified source.
9. **Turnaround** — synthetic (5 min), no verified source.
10. **DPR** — removed from project; no DPR-based claims remain.
11. **GTFS validity** — 2024-08-12 to 2025-12-31 (2024-25 timetable, not current 2026).
12. **18 vs 25 fleet** — 18 service + 7 maintenance = 25 total (from news 2026).
