## 1. Source Classification

Every parameter in this specification is tagged with one of:

| Tag | Meaning |
|-----|---------|
| `[DPR]` | Directly stated in the KMRL Phase-II DPR |
| `[DPR reference — unverified]` | Referenced in DPR text extracts, page/table pending verification |
| `[DERIVED FROM DPR]` | Mathematically computed from DPR values |
| `[EXTERNAL]` | From external authoritative source (unused in V1) |
| `[SYNTHETIC]` | Project assumption for experimentation |

**Rule:** No parameter is treated as `[DPR]` unless it can be verified against a page/table in the original DPR document. Values from text extracts are `[DPR reference — unverified]` until verified.

## 4. Data Quality Notes

### 4.1 19:00–20:00 DPR Inconsistency

The DPR publishes:
- Target headway: **5 min** → implies 12 departures/hour
- Stated departures: **15/hour**

These are mathematically inconsistent (60/5 = 12, not 15).

**Resolution:** Preserve both DPR values as-is. Do not "correct" either.

- Hard constraint (service coverage): `>= 15` departures
- Objective (headway deviation): target = 5 min

The resulting effective spacing (~4 min) will naturally reveal the inconsistency. This is a data-quality issue worth documenting.

### 4.2 UP/DOWN Direction

The DPR uses UP/DOWN labels. This specification treats:

- `UP` = increasing station sequence
- `DOWN` = decreasing station sequence

**Subject to verification against the DPR's route section.** If the DPR explicitly defines UP as Aluva → Tripunithura (or reverse), this interpretation will be updated.

## 5. Hard Constraints (R1–R12)

### R1 — Service Coverage `[DPR]`

For each hour `h` and direction `d`:

sum(trips[h][d]) >= required_departures[h][d]

**Implementation:** A trip-count constraint per (hour, direction).

**Validator check:** Count departures per (hour, direction) and compare against DPR table.

### R2 — Headway `[DPR]`

**R2a — Design headway (hard):**

departure[i+1] - departure[i] >= 90 seconds

for consecutive trips in the same direction.

**R2b — Target headway (soft — objective O2):**

minimize |actual_headway - target_headway[h]|

for consecutive trips in the same direction.

**Validator check:** No two departures in same direction closer than 90 sec.

### R3 — Operating Window `[DPR]`

05:00 <= passenger_departure
passenger_arrival <= 24:00

**Strict:** No trip crosses midnight in V1.

**Validator check:** All departure/arrival times within window.

### R4 — Fleet Availability `[DPR reference — unverified]`

Two constraints:

**R4a — Per-hour active rake bound (target design):**

```
active_service_rakes[h] <= 15 + activated_traffic_reserve[h]
```

**R4a — Per-hour active rake bound:**

active_service_rakes[h] <= 15 + activated_traffic_reserve[h]

rakes in maintenance block = 2 (always)

**Decision variables:**
- `activated_traffic_reserve[h] ∈ {0,1}` — per-hour Boolean
- `active_service_rakes[h]` — count of rakes in service during hour `h`

**Objective penalty (O7):** `sum_h activated_traffic_reserve[h]`

**Validator check:** Peak-hour active count <= 15 (+ 1 if activated).

### R5 — Rake Non-Overlap `[DPR]`

For each rake, no two activities overlap. Use CP-SAT interval variables:

model.AddNoOverlap(rake_intervals[rake_id])

**Validator check:** No rake is assigned overlapping time intervals.

### R6 — Terminal Turnaround `[DPR reference — unverified]`
turnaround_time >= 3 minutes

Applied between every consecutive trip on the same rake.

**Validator check:** All turnaround gaps >= 3 min.

### R7 — Running Time `[DERIVED FROM DPR]`

one_way_running_time = 10.715 km / 34 km/h * 60 min = 18.91 min

**Baseline value: 18.91 min.** Rounded to 19 min in integer-minute model.

**Validator check:** Each trip's duration matches configured running time.

### R8 — Depot Capacity `[DPR reference — unverified]`

**Info Park-2:**

rakes_stabled_at_InfoPark2 <= 2

**Muttom:** UNBOUNDED_FOR_V1

**Validator check:** Info Park-2 count <= 2.

### R9 — Maintenance Exclusivity `[DPR]`

A rake in maintenance cannot simultaneously be assigned to passenger service.

**Validator check:** No rake with active maintenance assigned to a trip.

### R10 — Maintenance Threshold `[DPR reference — unverified]`

Bogie overhaul interval: `~1,000,000 km` `[DPR reference — unverified]`

**Configurable.** A rake is due for maintenance when

cumulative_mileage >= maintenance_threshold_km

**Validator check:** No rake over threshold is assigned without a maintenance block.

### R11 — Deadhead / Positioning `[SYNTHETIC — NOT CONFIGURED]`

If `MUTTOM_TO_JLN_DEADHEAD_MIN` is None: model requires each rake's `initial_location` to match the terminal of its first assigned trip.

**Validator check:** Every rake's first trip starts at its initial location, OR has a modeled deadhead if configured

### R12 — Non-Service Window `[DPR]`

00:00–05:00: no passenger service
**Validator check:** No passenger trip starts before 05:00 or ends after 24:00.

## 6. Soft Objectives (O1–O7)

All weights are `[SYNTHETIC — INITIAL TUNING PARAMETERS]`.

### O1 — Minimize Passenger Waiting Time (weight = 10)
Headway-based expected waiting proxy.

### O2 — Minimize Headway Deviation (weight = 5)
Deviation from target headway per hour.

### O3 — Minimize Operational Delay (weight = 5)
Placeholder — no ML in V1, so inactive.

### O4 — Minimize Empty Running (weight = 2)
Placeholder — no deadhead modeled, so inactive.

### O5 — Minimize Depot Movements (weight = 2)
Placeholder — Muttom unbounded, so inactive.

### O6 — Balance Rake Utilization (weight = 3)
Minimize variance of accumulated mileage across rakes.

### O7 — Minimize Reserve Activation (weight = 1)
Penalty for activating traffic reserve during any hour.

### O8 — Crew Overtime (disabled in V1)
Deferred to Phase 3

## 10. Model Limitations (V1)

1. Muttom depot capacity — unbounded in V1
2. Deadhead — not configured
3. **Optimality gap is reported.** `solve.py` prints objective, best bound, and gap percentage after every solve. Claims about "optimized" now cite the actual gap value.
4. Crew scheduling — deferred to Phase 3
5. ML/XGBoost — deferred, no dependency
6. Passenger demand — no demand model; O1 uses headway-based proxy
7. UP/DOWN meaning — our interpretation, subject to DPR verification
8. 25-rake fleet — [EXTERNAL, unverified], not used
9. Traffic spare — currently used as 16th rake. Phase 1.5 refinement: add per-hour `activated_traffic_reserve[h]` variable, penalize via O7
10. DPR page/table references — 4 values unverified against original document
11. 15-rake feasibility — untested. Before final viva, solve with `SERVICE_RAKES = 15` and seconds-based running time (18.91 min) to determine if 16th rake is genuinely needed
